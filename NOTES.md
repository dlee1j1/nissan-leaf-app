# Notes

## 2026-09-02 — Fixing `make apk` (Android release build)

Branch: `fix/android-release-build` (4 commits). Not on `master` — fast-forward
`master` onto it if that's where these belong.

`make apk` now produces `nissan-leaf-app.apk` (~53 MB fat APK, arm64-v8a /
armeabi-v7a / x86_64). All 92 tests pass under the pinned SDK.

### Root causes

1. `Makefile` `setup` checked out the `stable` channel, so rebuilds drifted onto
   whatever Flutter stable had become (now 3.47.2). That new Flutter requires
   Gradle >= 8.14 (project was on 8.3) and defaults toward AGP 9.
2. Separately, this repo builds inside an **arm64** Linux container on an Apple
   Silicon host. Flutter ships the Android AOT toolchain (`gen_snapshot`) and the
   NDK strip/link tools as **x86_64 only**. They can run under Docker Desktop's
   Rosetta, but only if the x86_64 runtime libs exist and Flutter can find the
   binaries. Neither was true, so even after the Gradle fix the build failed at
   AOT, then packaged an unstripped 490 MB APK.

### Decisions I made that weren't specified

- **Matched the Flutter 3.47.2 Android template exactly** rather than doing the
  smallest bump past the 8.14 minimum: Gradle 9.3.1, AGP 9.1.0, Kotlin 2.4.0.
  The `android.newDsl=false` / `android.builtInKotlin=false` flags the Flutter
  migrator had already added to `gradle.properties` (uncommitted) only make sense
  on the AGP 9 path, so I committed them and finished that path.
- **Dropped `id "kotlin-android"`** from `android/app/build.gradle`. With
  `builtInKotlin=false` under AGP 9 the Flutter Gradle plugin applies KGP itself;
  an explicit apply now just prints a deprecation warning.
- **Bumped Java/Kotlin target 8 → 17.** Not strictly required to compile, but 8
  is unsupported by AGP 9 tooling and 17 is what the template uses.
- **Enabled core library desugaring** with `com.android.tools:desugar_jdk_libs:2.1.4`.
  `flutter_local_notifications` 18 requires it and AGP's AAR-metadata check now
  enforces that. Version is a current stable pick — bump if a plugin needs newer.
- **Forced every Android library subproject to the app's `compileSdk`** (a
  `subprojects { afterEvaluate { ... } }` block in `android/build.gradle`).
  `flutter_blue_plus_android` 3.0.0 hard-codes `compileSdkVersion 33` while its
  own AndroidX deps require 34+. I worked around it rather than changing the
  dependency.
- **Kept the container native arm64**; did *not* switch it to
  `platform: linux/amd64`. That would make everyday `flutter test` / `flutter run`
  run fully emulated and slow. Instead only the release AOT toolchain runs under
  Rosetta, via:
  - `Dockerfile`: `dpkg --add-architecture amd64` + the `:amd64` libs the
    toolchain links against.
  - `Makefile`: new `android-engine-shim` target (a prerequisite of `apk`) that
    symlinks `linux-arm64 -> linux-x64` inside each engine artifact dir so
    Flutter finds the x86_64 `gen_snapshot` where it expects an arm64-host one.
    No-op on x86_64 hosts.
- **Pinned `FLUTTER_VERSION := 3.47.2`** — the exact tag `stable` points at today,
  so no behaviour change now, just no more drift. `setup` re-aligns an existing
  `/opt/flutter` checkout to the tag.
- **`apk` target now takes the APK from `build/app/outputs/flutter-apk/`** (Flutter's
  canonical path) instead of `build/app/outputs/apk/release/`. Both are produced.
- **Committed `pubspec.lock`** — regenerated by `flutter pub get` on 3.47.2.
- **Set repo-local git identity** to `Dennis <dlee1j@gmail.com>` (matches existing
  history); git had no identity configured and refused to commit.
- Deleted a 125 MB `core` file (a Rosetta crash dump) that had been written into
  the repo root. Not committed.

### Left alone

- `docker-compose.yml` and `nissan_leaf_app/analysis_options.yaml` — both had
  pre-existing uncommitted edits (a trailing newline; an analyzer `exclude:`
  list). Not mine; left unstaged for you to handle.
- KGP-in-plugins warning for `flutter_foreground_task`, `location`,
  `shared_preferences_android`. These plugins apply the Kotlin Gradle Plugin
  themselves; Flutter warns that a *future* release will reject that. Not fatal
  now. Fix = upgrade those plugins once they support built-in Kotlin.
- `flutter_blue_plus` / `flutter_blue_plus_android` versions — worked around the
  compileSdk pin, didn't upgrade.
- App signing (still the debug keys), `flutter build appbundle`, debug/profile
  APK paths — out of scope, untouched.

### Couldn't verify

- **The APK was not installed or run.** No device/emulator attached and `make apk`
  doesn't need one. Verified only: it builds, is ~53 MB, and contains correctly
  stripped `libflutter.so` + AOT `libapp.so` for all three ABIs.
- **Clean `make docker-build` was not run.** The `Dockerfile` `:amd64` package
  list was validated by installing the same packages into the *running* container
  and completing a build; a from-scratch `docker-compose build` is unverified.
- **`android-engine-shim` on an empty `/opt/flutter` cache** wasn't exercised —
  the engine cache was already populated. The symlink loop itself was tested;
  its `flutter precache --android` step was not (and is `|| true`, so a failure
  there won't block `apk`).
- **Gradle daemon flakiness.** The daemon crashed mid-build twice
  ("Gradle build daemon disappeared unexpectedly"), each time leaving a Rosetta
  core dump; a plain re-run of `flutter build apk --release` succeeded both times.
  Looks like Rosetta flakiness under load rather than a config error, but I can't
  rule out memory pressure (daemon heap is `-Xmx4G`). If it recurs, try
  `org.gradle.daemon=false` or a smaller heap in `android/gradle.properties`.
- The first `make apk` in a fresh container will be slow (minutes): the Dart AOT
  compile runs under Rosetta. Subsequent builds are Gradle-cached and fast.
